## Calculation capture: exact stop sequence

All addresses are GBA bus addresses. ROM file offset = bus minus `0x08000000`; RAM values must be measured live. Console command names are from the [0.10.5 console implementation](https://github.com/mgba-emu/mgba/blob/0.10.5/src/debugger/cli-debugger.c); these procedures have **not** been executed locally. ### 1. Entry and caller

Set `break 0x08075970`, then `continue` and open/refresh the Gimmick page manually. On a hit:

```text
status
print/x r0
print/x r1
print/x lr
print/x sp
```

Record all registers and CPSR from `status`, stopped PC, and debugger point ID. Require CPSR bit `0x20` set for this routine. Let `g = r0 & 0xFF`, `P = r1`. The supported record window is g=1..50; an unexpected ID is evidence to investigate, not a reason to edit memory.

The candidate caller instruction is `(LR & ~1) - 4` for the ordinary Thumb BL path. Compare it with these seven known static call sites:

| Caller entry | BL instruction |
| --- | --- |
| `0x08076E28` | `0x08076E46` |
| `0x080770A8` | `0x0807715E` |
| `0x08078550` | `0x08078604` |
| `0x0807892C` | `0x08078ABE` |
| `0x08078CAC` | `0x08078D76` |

| `0x08080C84` | `0x08080EB4` |


## Battle trace procedure and stopping conditions

1. Use the separately prepared pre-action battle checkpoint. Record character, Gimmick ID/name, selector, upgrade, enemy identity, visible target HP and the intended minigame input sequence. Do not assume a menu cache survives the scene transition; measure its live pointer and relevant state again.
2. Remove noisy menu/UI stops. Add a read watchpoint at the **measured** P+0x0A to test whether that cache is used. Also test the chosen Gimmick's ROM `R+0x22`, state S[2], selected coefficient, and copied-record byte `0x03003F56 = 0x03003F34+0x22`, one at a time. `watch/r ADDRESS` records a reader; `watch/w ADDRESS` records a writer. Track IDs with `listw`; remove each with `delete ID` before the next probe.
3. For every actual battle hit, record trigger address, access width/type, PC/LR/CPSR, registers, nearby instruction bytes and before/after memory. Watchpoint stops may report after the access; verify the current/preceding instruction and mode. A menu/render access is not battle damage evidence. Readback may itself interact with access hooks, so distinguish an emulated instruction hit from a debugger inspection.
4. Follow the identified producer/consumer PCs using a short stepping sequence or an actual branch-target breakpoint. Record multipliers, divides, result comparisons, target pointers and stores. If the path is too large, record the precise stop and use those measured PCs for a bounded Ghidra follow-up; do not guess a next function.
5. Establish target HP address from live battle observations or differential memory inspection, then write-watch that **observed** address. The subsequent Gear-Yo test confirms target-0 HP at `0x03000A4E`; determine the actual target pointer on other actions. Demonstrate that the calculated damage is the operand used by an HP update, with HP before/after, including any saturation/knockout behavior. A numerically similar damage popup alone is insufficient to prove the path.
6. Record RNG only if a call/result enters this actual arithmetic path. The existing UI formula has no identified random term; do not introduce a speculative PRNG address or distribution.

If P+0x0A is never read in battle, investigate recomputation from R/S or the loader work copy. No hit does not prove the stat is irrelevant. Stop and report the last actual PC/operand when the value cannot be followed further. A runtime damage interpretation can become Confirmed only with the captured instruction chain and HP update; menu matches alone confirm the menu calculation for the tested cases.
